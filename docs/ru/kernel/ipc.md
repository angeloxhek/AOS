# Межпроцессное взаимодействие

Актуально для версии коммита 108.

Так как AOS построена на микроядерной архитектуре, межпроцессное взаимодействие (IPC) является кровеносной системой ОС. Любое обращение к файловой системе, отрисовка окна или получение ввода от клавиатуры происходит через отправку IPC-сообщений соответствующим драйверам.

AOS реализует **асинхронную очередь сообщений** с возможностью синхронного (блокирующего) ожидания на стороне клиента.

## 1. Структура сообщения

Все сообщения в системе имеют строго фиксированный размер и структуру (определена в `aos/ipc.h`).

```c
typedef struct message_t {
    apid_t   sender_pid;  // PID отправителя (Заполняется ядром!)
    uint32_t type;        // Тип сообщения (msg_type_t)
    uint32_t subtype;     // Подтип сообщения (msg_subtype_t)
    uint64_t id;          // Уникальный ID транзакции (Заполняется ядром!)
    uint64_t flags;       // Флаги сообщения (MSG_FLAG_*)
    uint64_t param1;      // Универсальный параметр 1
    uint64_t param2;      // Универсальный параметр 2
    uint64_t param3;      // Универсальный параметр 3
    uint8_t  data[64];    // Произвольная полезная нагрузка (64 байта)
} __attribute__((packed, aligned(8))) message_t;
```

Обычно поле param1 используется для указания команды (например, `VFS_CMD_READ`)

### Безопасность и концепция минимального доверия
Поля `sender_pid` и `id` **не контролируются пользователем**. При системном вызове отправки сообщения ядро принудительно перезаписывает `sender_pid` реальным PID'ом вызывающего процесса. Это гарантирует, что процесс не может подделать отправителя (спуфинг).

## 2. Типы, подтипы и флаги

Для маршрутизации сообщений внутри драйверов используются типы и подтипы.

**Типы (`msg_type_t`):**
Определяют глобальную подсистему, которой адресовано сообщение.
* `MSG_TYPE_VFS` - Файловая система
* `MSG_TYPE_WND` - Оконный менеджер
* `MSG_TYPE_AUTH` - Система прав доступа
* `MSG_TYPE_HARDWARE` - Аппаратные прерывания (отправляются ядром)
* и т.д.

**Подтипы (`msg_subtype_t`):**
Определяют направление и характер запроса.
* `MSG_SUBTYPE_QUERY` - Запрос от клиента к серверу (требует ответа)
* `MSG_SUBTYPE_SEND` - Односторонняя отправка (ответ не требуется)
* `MSG_SUBTYPE_RESPONSE` - Ответ сервера клиенту
* `MSG_SUBTYPE_PING` - Запрос от клиента к серверу (запрос разделен на блоки или диалог требуется в поддержке)
* `MSG_SUBTYPE_PONG` - Ответ сервера клиенту (запрос разделен на блоки или диалог требуется в поддержке)

**Флаги (`flags`):**
* `MSG_FLAG_NEW_ID` — Устанавливается ядром при инициации нового запроса (`ipc_send`).
* `MSG_FLAG_NORMAL` — Устанавливается ядром при ответе (`ipc_reply`).

## 3. Очереди и защита от DoS

Каждый процесс имеет свою очередь входящих сообщений в пространстве ядра. 
Чтобы один процесс не мог исчерпать память ядра, спамя другой процесс сообщениями, существует лимит очереди — `ipc_queue_limit` (по умолчанию 256 сообщений).

* Если очередь получателя заполнена, системный вызов отправки вернет ошибку `SYS_RES_ALREADY`.
* Процесс может изменить свой лимит с помощью `ipc_set_limit(pid, new_limit)`.
* Текущее количество сообщений в очереди можно узнать мгновенно (без системного вызова), прочитав поле `pending_msgs` из структуры PEB (Process Environment Block), адрес которой указан в макросе `PEB_VIRT_ADDR`.

## 4. Отправка и ответ (API ядра)

### `ipc_send`
```c
int64_t ipc_send(apid_t dest_pid, message_t* msg);
```
Инициирует новую транзакцию. Ядро генерирует уникальный `id` (глобальный счетчик), записывает его в сообщение, устанавливает флаг `MSG_FLAG_NEW_ID` и помещает в очередь `dest_pid`. 
**Возвращает:** Сгенерированный `id` транзакции (или код ошибки < 0).

### `ipc_reply`
```c
int64_t ipc_reply(message_t* in_msg, message_t* out_msg);
```
Используется сервером (драйвером) для ответа клиенту. Ядро берет `id` из `in_msg` и копирует его в `out_msg`, снимает флаг `NEW_ID` и отправляет сообщение обратно процессу `in_msg->sender_pid`.

## 5. Получение и фильтрация (AOSLIB)

Системные вызовы ядра (`__ipc_recv`, `__ipc_tryrecv`) просто извлекают первое сообщение из очереди ядра (**не локальной очереди**). Однако в реальных приложениях (особенно с GUI) процесс может ожидать ответа на конкретный запрос, пока в очередь сыплются события от мыши или клавиатуры.

Для решения этой проблемы `AOSLIB` предоставляет умную обертку с локальной очередью:

### `ipc_recv_ex` / `ipc_tryrecv_ex`
```c
void ipc_recv_ex(apid_t pid, msg_type_t type, msg_subtype_t subtype, uint64_t id, uint64_t flags, message_t* out_msg);
```
Эта функция позволяет **фильтровать** сообщения. 
Если из ядра приходит сообщение, которое *не соответствует* заданным фильтрам (например, пришло событие мыши, а мы ждем ответ от VFS с конкретным `id`), функция помещает это сообщение в **локальный связный список** внутри пользовательского пространства (`pending_head`) и продолжает вызывать ядро, пока не найдет нужное.

При последующих вызовах `ipc_recv` библиотека сначала проверяет локальный список, и только если он пуст, обращается к ядру.

*Примечание: Передача `0` в качестве фильтра (pid, type, id, flags) означает "любое значение".*

## 6. Передача больших данных

Поскольку размер поля `data` ограничен 64 байтами, передача буферов (чтение файлов, отрисовка графики) осуществляется через разделяемую память (Shared Memory).

**Стандартный паттерн взаимодействия:**

1. **Клиент:**
   * Выделяет SHM: `uint64_t shm_id = shm_alloc(size, &vaddr);`
   * Разрешает доступ серверу: `shm_allow(shm_id, driver_pid);`
   * Записывает данные в `vaddr` (если это запись).
   * Отправляет сообщение, передав `shm_id` в поле `data` или `param`.
   * Ждет ответа: `ipc_recv_ex(...)`.
   * Читает результат из `vaddr` (если это чтение).
   * Освобождает память: `shm_free(shm_id);`

2. **Сервер (Драйвер):**
   * Получает сообщение.
   * Маппит SHM в свое пространство: `void* buf = shm_map(shm_id);`
   * Выполняет работу с `buf`.
   * Освобождает маппинг в своем пространстве: `shm_free(shm_id);` *(Это не удаляет саму память, а лишь убирает её из адресного пространства сервера).*
   * Отправляет ответ: `ipc_reply(...)`.

*Пример из VFS (Чтение файла):*
```c
// Клиент (aos_vfs.c)
uint64_t shm_id = shm_alloc(count, &shm_vaddr);
shm_allow(shm_id, vfs_driver_pid);

req.param1 = VFS_CMD_READ;
*(uint64_t*)(req.data) = shm_id; // Передаем ID памяти

int64_t tx_id = ipc_send(vfs_driver_pid, &req);
ipc_recv_ex(vfs_driver_pid, MSG_TYPE_VFS, MSG_SUBTYPE_RESPONSE, tx_id, MSG_FLAG_NONE, &resp);

memcpy(user_buf, shm_vaddr, resp.param2); // Читаем результат
shm_free(shm_id); // Удаляем память
```
