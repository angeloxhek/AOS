# Виртуальная файловая система (VFS)

Актуально для версии коммита 108.

В операционной системе AOS **VFS не является частью ядра**. Это привилегированный системный демон (`VFSDRIVER.ELF`), загружаемый из `INITRD.TAR` на самом раннем этапе загрузки. 

VFS выступает центральным маршрутизатором для всех операций ввода-вывода в системе. Любое приложение, желающее открыть файл, прочитать данные с диска, получить список процессов или обратиться к аппаратному устройству, отправляет IPC-запросы драйверу VFS.

## 1. Архитектура дерева VFS

Внутри драйвера VFS файловая система представлена в виде иерархического графа узлов в оперативной памяти. Каждый узел (`vfs_node_t`) имеет имя, ссылку на родителя, список дочерних элементов и тип.

Существует 4 типа узлов:
1. **`VFS_TYPE_DIR`** — Виртуальная директория. Существует только в памяти VFS, служит для организации структуры (например, `/hw`, `/mnt`).
2. **`VFS_TYPE_DEVICE_FILE`** — Файл устройства. Чтение и запись в такой узел напрямую вызывает функции-обработчики внутри VFS (например, генератор случайных чисел `/hw/urandom` или прямой доступ к секторам диска `/hw/ide0/raw`).
3. **`VFS_TYPE_MOUNT_POINT`** — Точка монтирования. Указывает, что этот узел является корнем реальной файловой системы (FAT32, ProcFS и т.д.). Все запросы, уходящие глубже этого узла, делегируются соответствующему драйверу ФС.
4. **`VFS_TYPE_SYMLINK`** — Символическая ссылка. Содержит строковый путь, на который она указывает.

### Стандартная структура каталогов

При старте VFS автоматически формирует следующий скелет:
```text
/
|-- hw/                 # Аппаратные устройства
│   |-- null            # Пустое устройство (dev_read_null)
│   |-- zero            # Генератор нулей (dev_read_zero)
│   |-- urandom         # Генератор псевдослучайных чисел
│   |-- ide0/           # Физический диск (создается динамически)
│   |   |-- raw         # Прямой доступ ко всему диску
│   |   |-- v0/         # Первый раздел на диске
│   |       |-- raw     # Прямой доступ к секторам раздела
│   |       |-- fs      # Точка монтирования ФС этого раздела
|   |-- pci/            # Точка монтирования PCIFS (монтируется позже драйвером pcidriver)
├── sys/                # Системная информация
│   └── stat/
│       ├── uptime      # Время работы системы
│       └── flags       # Глобальные флаги ядра
├── tasks/              # Точка монтирования ProcFS (процессы и потоки)
├── mnt/                # Удобные ссылки на смонтированные ФС
│   ├── id/v0/          # Симлинк на /hw/ide0/v0/fs
│   └── SYSTEM/         # Симлинк по метке тома (Label)
└── boot/               # Симлинк на раздел, с которого загружена ОС
```

## 2. Разрешение путей

Когда процесс вызывает `open("/mnt/SYSTEM/folder/file.txt")`, VFS должен понять, к какому драйверу относится этот файл. За это отвечает механизм разрешения путей (`vfs_resolve`).

**Алгоритм работы:**
1. VFS разбивает путь на токены (по символу `/`).
2. Начиная от корня (`/`), VFS ищет совпадения имен среди дочерних узлов.
3. **Обработка симлинков:** Если найденный узел — `VFS_TYPE_SYMLINK` (например, `/mnt/SYSTEM` указывает на `/hw/ide0/v0/fs`), VFS подменяет текущий путь на целевой и начинает поиск заново. 
   * *Защита:* Для предотвращения зависания ядра из-за циклических ссылок (A -> B -> A), максимальная глубина рекурсии жестко ограничена 8 переходами. При превышении возвращается ошибка `VFS_ERR_SYMLINKLOOP`.
4. **Точка монтирования:** Как только VFS натыкается на узел `VFS_TYPE_MOUNT_POINT` (в нашем случае `/hw/ide0/v0/fs`), обход дерева VFS прекращается.
5. **Делегирование:** Оставшаяся часть пути (`folder/file.txt`) передается драйверу файловой системы, привязанному к этой точке монтирования.

## 3. Файловые дескрипторы и Изоляция

VFS ведет независимую таблицу файловых дескрипторов (FD) для каждого процесса в системе. Это гарантирует, что процесс А не сможет прочитать файл, открытый процессом Б, просто угадав номер FD.

* Внутри VFS существует список контекстов процессов (`vfs_proc_ctx_t`).
* Контекст привязан к PID процесса (`owner_pid`).
* Внутри контекста находится динамически расширяемый массив указателей на открытые файлы (`vfs_file_t`).
* Индекс в этом массиве (+1) и является тем самым файловым дескриптором, который возвращается клиентскому приложению.

**Структура открытого файла (`vfs_file_t`) хранит:**
* Текущее смещение (`offset`) — позицию каретки для чтения/записи.
* Флаги доступа (`VFS_FREAD`, `VFS_FWRITE`, `VFS_FAPPEND`).
* Уникальный `inode_id` (используется для блокировок).
* Указатель на внутренний хэндл конкретной файловой системы (`fs_file_handle_t`).

При каждом запросе `read`, `write` или `close` VFS проверяет, совпадает ли `sender_pid` из IPC-сообщения с `owner_pid` в контексте дескриптора.

## 4. Механизм взаимодействия

Поскольку VFS — это отдельный процесс, приложения общаются с ним через [IPC-сообщения](../kernel/ipc.md). Однако размер IPC-сообщения ограничен 112 байтами, чего недостаточно для передачи содержимого файлов.

Для передачи данных используется паттерн **Shared Memory (SHM)**.

**Жизненный цикл операции `read`:**
1. Клиентское приложение выделяет блок разделяемой памяти нужного размера (`shm_alloc`).
2. Клиент разрешает доступ к этой памяти процессу VFS (`shm_allow`).
3. Клиент отправляет IPC-сообщение `VFS_CMD_READ`, передавая FD, размер и **ID разделяемой памяти** (`shm_id`).
4. VFS получает сообщение, проверяет права на FD.
5. VFS маппит `shm_id` в свое виртуальное адресное пространство (`shm_map`).
6. VFS вызывает функцию чтения у драйвера ФС, передавая указатель на смаппленную память. Драйвер ФС (например, FAT32) читает сектора с диска прямо в эту память.
7. VFS освобождает маппинг (`shm_free`), обновляет `offset` файла и отправляет клиенту IPC-ответ с количеством прочитанных байт.
8. Клиент читает данные из своей памяти и окончательно удаляет SHM.

## 5. Блокировки файлов

VFS предоставляет механизм блокировок на уровне файлов (`VFS_CMD_FLOCK`), аналогичный системному вызову `flock` в Unix. Блокировки работают на уровне `inode_id`, поэтому они корректно обрабатывают ситуации, когда один и тот же файл открыт несколько раз под разными дескрипторами.

Поддерживаются два типа блокировок:
* **`VFS_LOCK_SH` (Shared)** — Разделяемая блокировка (обычно для чтения). Несколько разных процессов могут удерживать её одновременно.
* **`VFS_LOCK_EX` (Exclusive)** — Эксклюзивная блокировка (обычно для записи). Только один процесс может удерживать её. Если файл заблокирован эксклюзивно, любые попытки других процессов прочитать или записать в него (или получить свою блокировку) вернут ошибку `VFS_ERR_BUSY`.

## 6. Абстракции нижнего уровня

Сам по себе `vfsdriver.c` не умеет читать диски или понимать форматы файлов. Он делегирует эту работу трем подключаемым подсистемам (подробное описание каждой будет в отдельных документах):

1. **Блочный слой (Block Layer):** Отвечает за поиск физических дисков (IDE, AHCI), чтение их секторов и парсинг таблиц разделов (MBR, GPT). Предоставляет VFS готовые структуры `block_dev_t`. Подробнее здесь -> [Стандарт написания дисковых модулей](disk_modules.md)/[Стандарт написания парсеров разделов](part_modules.md) <-
2. **Драйверы ФС (FS Drivers):** Реализуют интерфейс `fs_driver_t` (`mount`, `open`, `read`, `readdir`). Подробнее здесь -> [Стандарт написания драйверов файловых систем](fs_modules.md) <-
3. **IPCFS (Проброс ФС через IPC):** Уникальный механизм AOS. Позволяет любому стороннему демону (например, драйверу PCI) зарегистрировать себя как файловую систему. VFS будет прозрачно перенаправлять все файловые операции клиента в IPC-сообщения этому демону.
