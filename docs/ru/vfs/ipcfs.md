# IPCFS: Проброс файловых систем через IPC

Актуально для версии коммита 108.

В традиционных монолитных ядрах (например, Linux) все драйверы файловых систем (EXT4, NTFS, FAT32) работают в пространстве ядра. В микроядерной архитектуре AOS центральный демон VFS (`VFSDRIVER.ELF`) берет на себя базовые ФС (FAT32, ProcFS). 

Однако, что если мы хотим добавить поддержку сложной сетевой файловой системы (NFS/SMB), FUSE-подобной ФС или виртуальной ФС для конфигурации оборудования (как `/sys` в Linux)? Встраивать весь этот код в VFS небезопасно и нарушает принцип изоляции.

Для решения этой проблемы в AOS создан механизм **IPCFS**. Он позволяет любому стороннему процессу (демону) зарегистрировать себя как провайдера файловой системы. VFS будет прозрачно перенаправлять все файловые операции клиента в IPC-сообщения этому демону.

## 1. Архитектура IPCFS

IPCFS состоит из двух частей:
1. **Внутренний драйвер VFS (`ipcfs_vfsmodule.c`)**: Это стандартный модуль ФС (реализующий `fs_driver_t`), который компилируется внутрь VFS. Его задача — перехватывать вызовы `read`, `write`, `open` и превращать их в IPC-сообщения.
2. **Удаленный драйвер (Remote FS Daemon)**: Это сторонний процесс (например, `pcidriver.c`), который слушает IPC-сообщения от VFS, обрабатывает их и возвращает результат.

### Как это выглядит для клиента?
Для клиентского приложения (например, файлового менеджера) нет абсолютно никакой разницы, обращается ли оно к FAT32 или к IPCFS. Клиент вызывает стандартные функции `vfs_open`, `vfs_read` из AOSLIB. Вся магия маршрутизации скрыта внутри VFS.

## 2. Жизненный цикл IPCFS

Рассмотрим процесс на примере драйвера PCI (`pcidriver.c`), который предоставляет виртуальную ФС для чтения конфигурации устройств.

### Этап 1: Регистрация
Когда драйвер PCI запускается, он отправляет VFS сообщение `VFS_CMD_REGISTER_FS` с именем `"pcifs"`.
* VFS получает сообщение, создает структуру `ipcfs_context_t`, сохраняет в ней PID драйвера PCI и имя `"pcifs"`.
* VFS добавляет этот контекст в глобальный список `ipcfs_registry`.

### Этап 2: Монтирование
Драйвер PCI просит VFS смонтировать свою файловую систему в определенную папку (например, `/hw/pci`), отправляя сообщение `VFS_CMD_MOUNT_FS`.
* VFS находит узел `/hw/pci`.
* VFS вызывает функцию `mount` внутреннего драйвера `ipcfs_driver`.
* `ipcfs_driver` отправляет IPC-сообщение `VFS_CMD_MOUNT_FS` обратно драйверу PCI, чтобы тот инициализировал свои внутренние структуры и вернул корневой хэндл (Root Handle).
* VFS создает узел `VFS_TYPE_MOUNT_POINT` и привязывает к нему полученный хэндл.

### Этап 3: Открытие файла
Клиент вызывает `vfs_open("/hw/pci/00:02.0/vendor")`.
* VFS разрешает путь, доходит до точки монтирования `/hw/pci` и понимает, что дальше работает `ipcfs_driver`.
* `ipcfs_driver` формирует IPC-сообщение `VFS_CMD_OPEN` с путем `00:02.0/vendor` и отправляет его драйверу PCI.
* Драйвер PCI парсит путь, находит нужное устройство, создает внутренний файловый дескриптор (Remote FD) и возвращает его VFS.
* VFS сохраняет этот Remote FD в своей таблице дескрипторов и возвращает клиенту локальный FD.

### Этап 4: Чтение данных
Клиент вызывает `vfs_read(fd, buf, size)`.
* Клиент выделяет Shared Memory (SHM) и отправляет запрос VFS.
* VFS понимает, что это IPCFS. Он выделяет **еще один блок SHM** и отправляет IPC-сообщение `VFS_CMD_READ` драйверу PCI, передавая Remote FD и ID разделяемой памяти.
* Драйвер PCI маппит SHM, пишет туда строку (например, `"0x8086\n"`), освобождает маппинг и отвечает VFS.
* VFS копирует данные в буфер клиента и отвечает ему.

## 3. Преимущества подхода

1. **Изоляция сбоев:** Если драйвер PCI упадет (например, из-за ошибки сегментации при парсинге пути), демон VFS продолжит работать. Упадет только точка монтирования `/hw/pci`.
2. **Безопасность:** Удаленный драйвер ФС не имеет прямого доступа к диску. Он может оперировать только теми данными, которые сам генерирует, или запрашивать чтение блоков у VFS через `VFS_CMD_BLOCK_READ`.
3. **FUSE "из коробки":** Разработчики могут писать драйверы файловых систем на любых языках (поддерживающих компиляцию под AOS) в Ring 3, используя стандартный AOSLIB, без необходимости перекомпилировать ядро или VFS.

## 4. Ограничения

* **Накладные расходы на IPC:** Каждая операция с файлом (даже `stat`) требует как минимум двух переключений контекста (VFS -> Remote FS -> VFS). Для высоконагруженных дисковых ФС (например, базы данных) это может стать узким местом. Поэтому базовые ФС (FAT32) встроены прямо в VFS.
* **Управление памятью:** Передача данных требует выделения и маппинга Shared Memory на каждом этапе, что увеличивает нагрузку на VMM ядра.
